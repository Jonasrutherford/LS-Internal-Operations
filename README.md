# LS Command

Lucid Studio's operating command center: fast, deterministic time logging on one
side, and analytics on revenue, labor, clients, capacity and task economics on the
other.

**Production:** https://lucid-os-original.vercel.app (Vercel project `lucid-os-original`)
**Database:** Supabase project `Lucid OS` (`sakwqqljepiflbbqbyuj`)

GitHub is the source of truth. Vercel is production. Supabase is the only place
data lives: nothing is kept in the browser.

## Stack

Next.js (App Router, TypeScript) and Supabase (Postgres, auth, row-level security).

```bash
npm install
cp .env.example .env.local     # Supabase URL and publishable key
npm run dev                    # http://localhost:3000
npm run build
npm test                       # finance, taxonomy and time math
```

## Data model

| Table | What it is |
|---|---|
| `people` | Team members. `role` is `admin` or `employee`. Sign-up is limited to lucidstudiollc.com and links to an existing row by email. |
| `clients`, `prospects`, `partners` | The three external relationships, kept apart. Lucid Studio itself is never a client. |
| `task_categories` | Groupings. `eligibility` is Internal, External or Both; `contexts` says which relationships an external category serves; `revenue_relationship` is Direct revenue, Pipeline or Operational. |
| `task_types` | The actual unit of work: expected minutes and where that number came from (measured, estimate, benchmark, contract), and an optional deliverable unit fixed per task. |
| `time_entries` | One row per session. Exactly one work type. A running timer is an entry with no `ended_at` (one per person). Parallel work points at its primary session with `parallel_of`. |
| `entry_participants` | Teammates on joint work. |
| `contracts`, `contract_price_changes` | One contract per client relationship; price changes keep history. |
| `billing_events` | Every bill: retainer cycles, one-off projects, hourly work, ad commission, additional charges, other income. Revenue counts when paid. |
| `expenses` | One-off payments and recurring rules (monthly, quarterly, annually), each vendor or contractor its own line. |
| `revenue_goals`, `app_settings` | Annual goal and payout rules. |
| `audit_log` | Every change to money, the taxonomy or someone else's time. |

The trigger `check_time_entry` refuses any entry that mixes work types: internal
work cannot carry a client, an internal-only category or task can never be logged
as external, and a task must belong to its category. The UI applies the same rule
(`lib/taxonomy.ts`), so irrelevant options are never shown in the first place.

Nothing referenced by history is deleted. Taxonomy and relationships are archived;
entries, bills and expenses are marked `deleted`.

Migrations live in `supabase/migrations/`. The taxonomy seed is generated by
`python3 scripts/taxonomy.py`; after that the taxonomy is edited in
System Admin > Task Taxonomy.

## Roles

Employees: Dashboard, Start / Log, Time Log, Tasks, Performance, Settings. They log
their own time and can see company work.

Admins: everything, plus Company Projections, Revenue, Clients, Payouts / Expenses
and System Admin, and corrections to anyone's time.

Enforced by row-level security in Postgres and by `requireAdmin()` /
`assertAdmin()` on the server. Hidden navigation is a convenience, not the control.

## Baseline and history

October 1, 2026 is the clean logging baseline. Data from the previous app (which
kept it in each browser) moves into Supabase once, from System Admin > Data Import,
opened in the browser that holds it. The import is idempotent: every row carries a
`legacy_ref`.

## Tests

- `npm test`: finance, payouts, goal pace, taxonomy filtering, work items, time zone.
- `tests/ui-flows.mjs`: drives the real UI (logging rules, admin, permissions,
  mobile) against `tests/mock-supabase.mjs`, a local stand-in. See the file header.
- Row-level security and the integrity triggers were verified against the real
  database inside a rolled-back transaction.
